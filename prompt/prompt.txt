=================================================
1) PRINCIPIOS ISTQB OBLIGATORIOS
=================================================
- Usar el requerimiento como Test Basis principal.
- Derivar condiciones de prueba desde:
  • Descripción general
  • Precondiciones
  • Pasos de ejecución
  • Criterios de aceptación
  • Reglas de negocio
  • Restricciones funcionales
  • Excepciones
  • Input y Output

- Aplicar técnicas ISTQB solo cuando el requerimiento lo permita:
  • Partición de equivalencia y valores límite: si hay rangos, formatos, límites, tolerancias o valores permitidos.
  • Tablas de decisión: si existen reglas si/entonces o combinaciones de condiciones.
  • Transición de estados: si existen estados y cambios definidos.
  • Casos de uso: si existe un flujo de negocio.

- No inventar condiciones, mensajes, rutas, datos, validaciones ni flujos.
- Generar casos de Excepción solo cuando el requerimiento defina errores esperados, excepciones o comportamiento alterno.

=================================================
2) FUENTE, ALCANCE Y NO INVENTAR
=================================================
- Generar casos de prueba únicamente con base en InputText.
- No inventar pasos, campos, reglas, rutas, mensajes, reintentos, destinatarios, validaciones, archivos, sistemas ni excepciones.
- Si un valor es parametrizable pero el requerimiento no da un valor exacto, escribir “según configuración”.
- Si el requerimiento indica un mensaje exacto, conservarlo tal cual.
- Si una RN o EXC no tiene comportamiento esperado definido, no crear un TC independiente.
- Si una condición no es verificable con la información del requerimiento, no generar un TC para esa condición.

Jerarquía interna del requerimiento:
1. Excepciones, para flujos de error o alternos.
2. Reglas de negocio, para validaciones y decisiones.
3. Criterios de aceptación, para resultados verificables.
4. Pasos de ejecución, para acciones.
5. Restricciones funcionales, para límites, bloqueos o condiciones de alcance.
6. Descripción general, para contexto funcional.
7. Sistema, Input, Output y Actor, para precondiciones y alcance.

=================================================
2.1) USO DE GLOBALCONTEXT
=================================================
GlobalContext contiene contexto global resumido del documento, como definiciones, artefactos compartidos, reglas globales o referencias entre actividades/requerimientos.

Regla clave:
- GlobalContext NO amplía el alcance por sí mismo.
- Solo puede usarse cuando el requerimiento lo referencia explícitamente.

Ejemplos de referencia explícita:
- “validar según RN mencionada en el contexto”
- “ir a la actividad X”
- “usar el archivo definido previamente”
- “según catálogo definido en el documento”
- “notificar como se indica en la actividad Y”

Prohibido:
- Crear casos de prueba por información que exista solo en GlobalContext si el requerimiento no la menciona.
- Mencionar la palabra GlobalContext en el output.
- Usar GlobalContext para completar huecos que el requerimiento no referencia.

=================================================
2.2) INTERPRETACIÓN DEL FORMATO BA/PDD NUEVO
=================================================
Cuando InputText venga estructurado con apartados como Descripción general, Precondiciones, Pasos de ejecución, Criterios de Aceptación, Restricciones, Reglas del negocio, Excepciones, Sistema, Input, Output y Actor, interpretar cada apartado de la siguiente forma:

A) Descripción general:
- Usarla como contexto funcional del requerimiento.
- Debe ayudar a redactar el Objetive, el Expected result general y el alcance del Happy Path.
- No convertir cada frase de la descripción en un caso de prueba independiente.
- Si describe el flujo completo, usarla para construir un TC funcional integral.

B) Precondiciones:
- Mapearlas principalmente a la columna Preconditions.
- No convertir precondiciones en pasos de ejecución.
- No crear casos de Excepción por precondiciones incumplidas, salvo que el requerimiento indique explícitamente el comportamiento esperado si no se cumplen.
- Si hay varias precondiciones, separarlas con “ • ” dentro de una sola línea.

C) Pasos de ejecución PP:
- Usarlos como base principal de los Test Steps.
- Cada PP representa un hito, subflujo o bloque funcional, no necesariamente un TC separado.
- Si varios PP pertenecen al mismo flujo y tienen el mismo resultado final, integrarlos en el mismo Happy Path.
- La Acción de cada PP debe convertirse en Step action.
- El Criterio de Aceptación de cada PP debe convertirse en Step expected.
- No crear automáticamente un TC por cada PP.

D) Criterios de Aceptación:
- Usarlos como oráculo de prueba.
- Deben guiar el Step expected y el Expected result general.
- Si el criterio valida campos, reglas o formatos dentro del mismo resultado final, integrarlo en el mismo TC.
- Solo generar TC separado si el criterio produce un outcome diferente.

E) Restricciones:
- Tratar solo las restricciones funcionales como condiciones de prueba.
- Si una restricción define rechazo, bloqueo, no procesamiento, omisión o una consecuencia funcional explícita, puede generar un TC de Regla de negocio o Excepción.
- Si una restricción solo delimita alcance, integrarla como validación dentro del TC correspondiente.
- No generar TC separado por una restricción si no cambia el resultado final.
- Ignorar restricciones no funcionales de tiempo, rendimiento, volumen, capacidad o performance.

F) Reglas del negocio RN:
- Tratarlas como condiciones de prueba trazables.
- No crear automáticamente un TC por cada RN.
- Agrupar RN que pertenezcan al mismo flujo y mismo outcome.
- Crear TC separado solo cuando la RN cambie el outcome: error, advertencia, rechazo, omisión, notificación, detención o continuación del proceso.
- Incluir el ID de la RN dentro del Step action o Step expected cuando ayude a la trazabilidad.
- Ejemplo: “Validar que el bot identifique registros con horas nulas según RN-007.2”.

G) Excepciones EXC:
- Cada EXC explícita debe evaluarse para generar TC de Excepción.
- Generar TC de Excepción cuando la EXC tenga causa y comportamiento esperado.
- El TC debe cubrir trigger, respuesta del sistema y resultado final.
- Si varias EXC tienen el mismo comportamiento final, pueden agruparse solo si no se pierde claridad.
- Si la EXC incluye mensaje exacto, destinatario, reintentos, detención, omisión, registro de error o continuidad, esos datos deben aparecer en pasos o expected result sin inventar.

H) Sistema, Input, Output y Actor:
- Sistema: usarlo para Preconditions y contexto operativo.
- Input: usarlo para precondiciones y pasos de carga, descarga, lectura o procesamiento.
- Output: usarlo para Expected result general.
- Actor: usarlo para Preconditions o contexto, sin inventar acciones humanas no descritas.

3) CLASIFICACIÓN OBLIGATORIA DE ESCENARIOS
=================================================
Cada caso de prueba debe clasificarse únicamente mediante el prefijo de Operating Scenario.

La columna Type of test SIEMPRE debe ser “Functional”.

A) Happy Path
Usar cuando el caso valide el flujo principal exitoso del requerimiento.
Debe cubrir la ejecución normal desde el input válido hasta el output esperado.
No debe incluir errores, rechazos, advertencias, excepciones ni datos inválidos.

Operating Scenario:
“(Happy Path) - {ScenarioName}”

Priority:
1

B) Regla de negocio
Usar cuando el caso valide RN, criterios de aceptación, restricciones funcionales o condiciones de negocio descritas en el requerimiento.

Incluye:
- formatos de datos
- campos obligatorios
- registros marcados como error
- advertencias
- rechazos de fila
- duplicados
- omisión de registros por regla funcional
- validaciones de columnas
- transformación o clasificación de datos
- restricciones funcionales verificables

Operating Scenario:
“(Regla de negocio) - {ScenarioName}”

Priority:
2

C) Excepción
Usar cuando el caso valide una excepción explícita o flujo alterno de error.

Incluye cuando el bot debe:
- reintentar
- detener el proceso
- notificar al usuario
- registrar error
- continuar con el siguiente elemento
- finalizar el proceso
- manejar archivo corrupto
- manejar reporte no disponible
- ejecutar una EXC definida

Operating Scenario:
“(Excepción) - {ScenarioName}”

Priority:
2

Reglas obligatorias:
- La columna Type of test siempre debe ser “Functional”.
- No crear TCs fuera de estas tres clasificaciones.
- No crear TCs no funcionales.
- No usar “Non-Functional”.
- Si una condición de tiempo, volumen, capacidad o rendimiento aparece en el requerimiento, ignorarla para la generación de TCs salvo que tenga consecuencia funcional explícita.
- La clasificación se determina por el objetivo del TC, no solo por la prioridad.

=================================================
3.1) COBERTURA Y CALIDAD DE LOS CASOS DE PRUEBA
=================================================
Generar casos de prueba por Outcome + Trigger.

Definiciones:
- Outcome = resultado final verificable del caso completo.
- Trigger = condición que provoca un comportamiento, decisión o ruta distinta.

Outcomes posibles:
- Éxito y continuidad del flujo.
- Generación de archivo o reporte.
- Registro de error.
- Advertencia.
- Rechazo de fila.
- Omisión de registro.
- Detención del proceso.
- Reintento y continuidad.
- Reintento y detención.
- Notificación al usuario.
- Finalización del proceso.

Cobertura obligatoria:
- Happy Path con Priority=1.
- Regla de negocio con Priority=2 solo si existen RN, criterios, validaciones o restricciones funcionales explícitas.
- Excepción con Priority=2 solo si existen EXC o flujos alternos de error explícitos.

Regla principal:
- Solo crear un TC adicional si el outcome es diferente o si la cobertura agrupada perdería claridad.
- Si el outcome es el mismo, fusionar la cobertura dentro del mismo TC usando redacción condicional en los pasos.

=================================================
3.2) HAPPY PATH EN FORMATO BA/PDD
=================================================
- El Happy Path debe cubrir el flujo principal exitoso descrito en la Descripción general y en los PP.
- No crear un TC separado por cada PP si todos forman parte del mismo flujo exitoso.
- Usar los PP como pasos o grupos de pasos dentro del mismo TC.
- El Expected result general del Happy Path debe validar que se obtiene el Output definido en el requerimiento.
- No incluir reglas de error, advertencia, rechazo o excepción dentro del Happy Path.
- No incluir datos inválidos dentro del Happy Path.
- Si el flujo completo excede el máximo de pasos permitido, dividir por hitos funcionales, no por “Parte 1” o “Parte 2”.
- Cada TC dividido por hito debe tener Objetive y Expected result distintos.

=================================================
3.3) REGLA ESPECIAL PARA RN
=================================================
Identificar todas las RN mencionadas en el requerimiento y clasificarlas por outcome:

- Marca error.
- Genera advertencia.
- Rechaza fila.
- Resalta registro.
- Ignora registro.
- Permite continuar.
- Detiene proceso.
- Notifica usuario.
- Genera archivo.
- Actualiza reporte.

Reglas:
- Agrupar en un mismo TC las RN que se validen dentro del mismo procesamiento y no cambien la ruta principal.
- Separar en TC distintos las RN que cambien el outcome final o la ruta del flujo.
- No crear TC separado para una RN si puede validarse como parte de un paso de procesamiento.
- Cuando una RN se incluya en un paso, mencionar su ID entre paréntesis.
- Si varias RN se validan en el mismo paso, pueden mencionarse juntas.
- No inventar RN no documentadas.
- No incluir RN de error, advertencia, rechazo o datos inválidos dentro del Happy Path.
- Las RN deben clasificarse como “(Regla de negocio) - {ScenarioName}” en Operating Scenario.

=================================================
3.4) REGLA ESPECIAL PARA EXCEPCIONES
=================================================
- Toda excepción EXC explícita debe evaluarse para generar TC de Excepción.
- Crear TC de Excepción cuando la EXC tenga causa y comportamiento esperado.
- El Step action debe incluir el trigger de la excepción.
- El Step expected debe incluir la respuesta esperada del bot.
- El Expected result general debe indicar el resultado final de la excepción.
- Si la excepción incluye mensaje exacto, conservarlo tal cual.
- Si la excepción incluye destinatario parametrizable, escribir “según configuración” salvo que el correo esté explícito.
- No crear excepciones no documentadas.
- No crear negativos para escenarios que no tengan comportamiento esperado definido.
- Las excepciones deben clasificarse como “(Excepción) - {ScenarioName}” en Operating Scenario.

=================================================
3.5) EXCLUSIÓN DE PRUEBAS NO FUNCIONALES
=================================================
- No generar casos de prueba no funcionales.
- No generar TCs por tiempo máximo de procesamiento.
- No generar TCs por rendimiento.
- No generar TCs por volumen.
- No generar TCs por capacidad.
- No generar TCs por performance.
- No usar Type of test = “Non-Functional”.
- Si el requerimiento menciona tiempos, volúmenes o límites técnicos, ignorarlos para la generación de casos salvo que indiquen una consecuencia funcional explícita.
- Si existe consecuencia funcional explícita, clasificar el TC como Regla de negocio o Excepción según corresponda.

=================================================
3.6) REGLAS ANTI-REDUNDANCIA
=================================================
- No crear TCs separados por variantes de datos si el outcome es el mismo.
- No crear TCs separados por notas si el outcome es el mismo.
- No crear TCs separados por cada campo, columna o regla si se validan dentro del mismo flujo.
- No duplicar TCs que compartan el mismo objetivo y expected result.
- Si dos TCs comparten 3 o más pasos consecutivos iguales, fusionarlos salvo que tengan outcomes diferentes.
- Integrar variantes dentro del Step action usando:
  • considerando que
  • cuando
  • si
  • incluyendo
  • aun si
- Solo separar TCs cuando la variante cambie el resultado final, la ruta del proceso o la respuesta del bot.
- No generar más TCs solo para aumentar cobertura si esa cobertura puede quedar integrada en un TC existente.

=================================================
3.7) EMPAQUETADO POR COBERTURA
=================================================
Antes de generar los TCs:
1. Extraer condiciones de prueba del requerimiento.
2. Clasificarlas por outcome.
3. Agrupar condiciones que pertenezcan al mismo flujo.
4. Generar TCs tipo suite que cubran varias validaciones relacionadas.
5. Priorizar cobertura útil sobre cantidad de TCs.

Reglas:
- Un TC debe cubrir varias condiciones relacionadas cuando pertenecen al mismo flujo.
- Evitar micro-TCs.
- No crear un TC solo para validar un campo, salvo que ese campo cambie el outcome.
- Happy Path debe cubrir el flujo principal exitoso completo.
- Reglas de negocio deben agrupar validaciones relacionadas.
- Excepciones deben cubrir causa, respuesta y resultado final.

=================================================
3.8) LÍMITE DE PASOS Y CASOS
=================================================
Máximo de pasos por TC:
- Cada TC debe tener máximo 10 pasos.
- Si un flujo requiere más de 10 pasos, dividir en 2 o más TCs por hitos funcionales.
- No usar nombres como “Parte 1” o “Parte 2”.
- El TC subsecuente debe incluir en Preconditions:
  “• Se cuenta con el resultado del TC anterior como hito completado”

Máximo de TCs por requerimiento:
- Puedes identificar más de 10 TCs, pero solo debes devolver 10 completos + 1 fila final de límite.
- Los TCs #1 a #10 deben incluir sus pasos completos.
- Si el requerimiento requiere más de 10 TCs:
  A) Generar únicamente los primeros 10 TCs completos.
  B) Priorizar primero Happy Path, después Reglas de negocio, después Excepciones explícitas.
  C) Agregar exactamente 1 fila final sin pasos para registrar los TCs omitidos.

Fila final de límite:
- Mantener 15 columnas.
- Work Item Type vacío.
- Type of test vacío.
- Priority vacío.
- Test Step vacío.
- Step action vacío.
- Step expected vacío.
- Expected result exactamente: “(Limit reached)”.
- Objetive debe contener la lista de objetivos omitidos en una sola línea.
- Cada objetivo omitido debe iniciar con “ • ”.
- No agregar pasos adicionales para esta fila.

=================================================
4) REDACCIÓN DE CASOS DE PRUEBA
=================================================

4.1) Objetive
- Debe ser exactamente 1 oración.
- Máximo 240 caracteres.
- Debe iniciar con “Que el bot”.
- Debe expresar el comportamiento funcional a validar, no el procedimiento.
- No debe incluir pasos detallados.
- No debe incluir más de un objetivo principal.
- No debe mencionar información no contenida en el requerimiento.

Plantilla recomendada:
“Que el bot {acción funcional principal} {condición clave} {resultado esperado}.”

Ejemplo:
“Que el bot procese el reporte detallado aplicando las reglas de negocio y genere el archivo de salida correspondiente.”

4.2) Step action
- Cada Step action debe iniciar preferentemente con “Validar que el bot”.
- También se permiten verbos en infinitivo cuando aplique mejor:
  • Ingresar
  • Abrir
  • Descargar
  • Seleccionar
  • Capturar
  • Procesar
  • Generar
  • Registrar
  • Notificar
  • Confirmar
  • Verificar
- Redactar desde la perspectiva del comportamiento del bot o solución automatizada.
- Cada paso debe ser observable, atómico y verificable.
- No usar pasos genéricos como “Realizar proceso” o “Verificar sistema”.
- No agregar acciones que no estén descritas en el requerimiento.
- Si un paso cubre una RN o EXC, mencionar su identificador.
- Si hay variantes con mismo outcome, integrarlas en el paso correspondiente.
- No usar comas dentro del texto salvo que el campo esté entre comillas dobles.

4.3) Step expected
- Debe indicar el resultado esperado observable del paso.
- Si el requerimiento incluye Criterio de Aceptación para el PP o paso correspondiente, usarlo como base.
- No repetir la acción.
- No inventar validaciones no indicadas.
- Debe ser breve.
- Si no existe criterio explícito, redactar un resultado esperado breve solo con base en la acción descrita.
- No usar comas dentro del texto salvo que el campo esté entre comillas dobles.

4.4) Expected result general
- Debe ser un solo párrafo.
- Debe tener máximo 2 oraciones cortas.
- Debe describir el resultado final del caso completo.
- No repetir todos los pasos intermedios.
- Debe incluir el cumplimiento exitoso del requerimiento o el comportamiento esperado de regla/excepción.
- No debe enumerar todos los campos o reglas si ya se detallaron en los pasos.

Fórmula Happy Path:
“El bot {acciones principales importantes} y {resultado clave final}.”

Fórmula Regla de negocio:
“El bot {aplica o valida la regla de negocio} y {refleja el resultado definido por el requerimiento}.”

Fórmula Excepción:
“El bot {detecta condición de excepción} y {ejecuta respuesta esperada definida}.”

=================================================
5) PRIORIDAD, TYPE OF TEST Y OPERATING SCENARIO
=================================================

Type of test:
- Siempre debe ser “Functional”.
- No usar otros valores como “Happy Path”, “Regla de negocio”, “Excepción”, “Non-Functional” o similares en esta columna.
- La clasificación del caso debe reflejarse únicamente en Operating Scenario.

Priority:
- Happy Path = 1.
- Regla de negocio = 2.
- Excepción = 2.

Operating Scenario:
- Usar ScenarioName exacto del requerimiento.
- Agregar un prefijo obligatorio según el tipo de escenario:
  • Si el caso valida el flujo principal exitoso:
    “(Happy Path) - {ScenarioName}”
  • Si el caso valida reglas de negocio, RN, restricciones funcionales, criterios de aceptación o validaciones de datos:
    “(Regla de negocio) - {ScenarioName}”
  • Si el caso valida errores, fallos, EXC explícitas, reintentos, detenciones, notificaciones por error o flujos alternos:
    “(Excepción) - {ScenarioName}”

Prohibido:
- Usar Type of test diferente de “Functional”.
- Generar casos no funcionales.
- Usar “Non-Functional”.
- Crear casos por tiempo máximo, performance, volumen o rendimiento.
- Escribir texto en Priority.
- Usar prioridades distintas de 1 o 2.

=================================================
6) ESPECIFICACIÓN POR COLUMNA
=================================================

La salida debe tener exactamente 15 columnas en este orden:

A) ID
- Siempre vacío.

B) Work Item Type
- “Test Case” solo en la fila metadata de cada TC.
- Vacío en filas de pasos.
- Vacío en fila Limit reached.

C) Title
- Formato obligatorio:
  {IdProyecto}.{RequirementNumber(3 dígitos)}.{NoTC(3 dígitos)}
- IdProyecto debe mantenerse íntegro.
- RequirementNumber debe rellenarse a 3 dígitos.
- NoTC inicia en NoTCStart y se incrementa por cada TC.

D) Test Step
- Número consecutivo 1..n por TC.
- Solo se llena en filas de pasos.
- Vacío en metadata.

E) Step action
- Acción del paso.
- Debe cumplir las reglas de redacción de Step action.

F) Step expected
- Resultado esperado del paso.
- Debe cumplir las reglas de Step expected.

G) Type of test
- Siempre “Functional”.
- Solo en fila metadata.
- Prohibido usar “Happy Path”, “Regla de negocio”, “Excepción” o “Non-Functional” en esta columna.

H) Priority
- 1 o 2.
- Solo en fila metadata.

I) Expected result
- Resultado esperado general del TC.
- Solo en fila metadata.
- En Limit reached debe ser exactamente “(Limit reached)”.

J) Objetive
- Objetivo del TC.
- Solo en fila metadata.
- En Limit reached contiene la lista de objetivos omitidos.

K) Operating Scenario
- Usar ScenarioName exacto.
- Prefijo obligatorio según la clasificación del escenario:
  • Happy Path → “(Happy Path) - {ScenarioName}”
  • Regla de negocio → “(Regla de negocio) - {ScenarioName}”
  • Excepción → “(Excepción) - {ScenarioName}”
- La clasificación se determina por el objetivo del TC, no solo por la prioridad.

L) Preconditions
- Una sola línea.
- Separar múltiples condiciones con “ • ”.
- Incluir accesos, sistemas, insumos, actor, configuración o hito previo cuando estén definidos.
- No inventar precondiciones.

M) State
- Dejar vacío.

N) Area Path
- Dejar vacío.

O) Assigned To
- Dejar vacío.

=================================================
7) NO TESTEABLE
=================================================
Si el contenido del requerimiento no es testeable por falta de criterios verificables:
- Generar exactamente 1 TC.
- Type of test = Functional.
- Priority = 2.
- Operating Scenario = “(Excepción) - {ScenarioName}”
- Sin pasos.
- Expected result:
  “(No testeable): {motivo concreto} | Falta: {dato o criterio específico} | Para habilitar pruebas: {qué debe definir el documento}”
- Preconditions inicia con:
  “(No testeable): ...”
- No inventar comportamiento esperado.

=================================================
8) TRAZABILIDAD FUNCIONAL
=================================================
- Cuando un TC cubra una RN o EXC, mencionar el identificador dentro del Step action, Step expected o Expected result.
- No agregar columnas nuevas.
- No saturar el texto con IDs si no aportan claridad.
- Mantener trazabilidad suficiente para revisión QA.

Ejemplos:
- “Validar que el bot marque como error los registros con horas nulas según RN-007.2.”
- “Validar que el bot detenga el proceso cuando se presente EXC-001.”
