Actúa como un QA Lead Senior especializado en análisis funcional de documentos PDD/FDD y planeación de insumos para pruebas.

Analiza integralmente el PDD o FDD proporcionado y realiza dos tareas en una sola ejecución:

1. Extraer los requerimientos funcionales principales que serán utilizados como alcance funcional en un Plan Estratégico de Pruebas (PEP).
2. Extraer la tecnología usada para construir la solución, tomando como fuente principal el PDD/FDD.
3. Extraer la información operativa y volumétrica del proceso para calcular el plan de insumos de testing.

Analiza exclusivamente el documento proporcionado.

No inventes información.

No uses conocimiento externo para completar campos faltantes.

Devuelve únicamente JSON válido, sin markdown, comentarios ni texto adicional.

Usa null cuando un dato individual no haya sido encontrado y [] cuando no existan elementos para una lista.

==================================================
1. EXTRACCIÓN DE REQUERIMIENTOS
==================================================

Identifica los requerimientos, acciones o pasos funcionales PRINCIPALES del proceso futuro.

Estos títulos serán insertados directamente en el PEP.

IMPORTANTE:
No extraigas encabezados de tablas, encabezados de índice, nombres de columnas, tipos de prueba, secciones generales ni subsecciones internas como requerimientos.

Un requerimiento funcional principal debe representar una acción, funcionalidad o comportamiento específico que será probado.

Devuelve únicamente el título funcional limpio del requerimiento.

No incluyas en la salida final:
- IDs estructurados del proyecto;
- prefijos técnicos;
- claves internas del requerimiento;
- numeración de sección que no forme parte del nombre funcional.

==================================================
FORMATOS CONOCIDOS
==================================================

Los requerimientos normalmente pueden encontrarse en alguno de los siguientes formatos:

--------------------------------------------------
A. PDD Beecker - "Acciones detalladas del proceso TO-BE"
--------------------------------------------------

Los requerimientos pueden encontrarse dentro de una sección llamada:

"Acciones detalladas del proceso TO-BE"

Esta sección comúnmente puede estar numerada como:

"2.4 Acciones detalladas del proceso TO-BE"

La numeración puede variar o no aparecer. Lo importante es identificar la sección "Acciones detalladas del proceso TO-BE" o una sección equivalente de proceso TO-BE.

Ejemplo de estructura jerárquica:

2 - Pantalla principal
2.1 - Indicadores
3 - Pantalla de consulta
3.1 - Filtros de búsqueda

En este tipo de estructura existe una jerarquía de requerimientos.

Debes devolver únicamente los requerimientos principales.

Un requerimiento numerado con más niveles representa normalmente un subrequerimiento del elemento principal anterior.

Ejemplos:

2       = requerimiento principal
2.1     = subrequerimiento
2.1.1   = subrequerimiento de nivel inferior

3       = requerimiento principal
3.1     = subrequerimiento

Para el ejemplo anterior devuelve únicamente:

"Pantalla principal"
"Pantalla de consulta"

NO devuelvas:

"Indicadores"
"Filtros de búsqueda"

También puede existir el formato:

1. Nombre de la acción: Consultar información
2. Nombre de la acción: Validar datos

En este caso devuelve:

"Consultar información"
"Validar datos"

También puede existir el formato numerado:

1. Obtener información de entrada
Descripción general: ...

2. Procesar información
Descripción general: ...

En este caso devuelve:

"Obtener información de entrada"
"Procesar información"

--------------------------------------------------
B. FDD con identificadores estructurados de requerimiento
--------------------------------------------------

Este formato es común en FDD donde los requerimientos aparecen dentro de tablas o bloques de "Process Steps".

REGLA CRÍTICA:
Si el documento contiene identificadores estructurados con el patrón:

[PREFIJO].[NNN].[NNN]

por ejemplo:

ABC.001.001
ABC.001.002
ABC.001.003

entonces esos identificadores son la fuente principal para detectar requerimientos.

En este formato usa el identificador estructurado únicamente para:

1. Confirmar que se trata de un requerimiento válido.
2. Delimitar el bloque del requerimiento.
3. Diferenciarlo de encabezados de sección, tablas o contenido interno.

PERO:
No incluyas el identificador estructurado en la salida final.

Extrae solamente el título funcional asociado al identificador.

Ejemplo sintético:

ABC.001.001 Start process
ABC.001.002 Validate input data
ABC.001.003 Generate output

Devuelve:

"Start process"
"Validate input data"
"Generate output"

Si el Project ID fue detectado previamente, por ejemplo:

ABC.001

entonces prioriza únicamente los identificadores que comiencen con:

ABC.001.

Ejemplo:

Project ID: ABC.001

IDs válidos:

ABC.001.001
ABC.001.002
ABC.001.003

IDs no válidos:

XYZ.999.001
REQ-01
4.1
4.2

No extraigas como requerimientos:

- Encabezados de sección como "4.1 Configurar proceso".
- Encabezados de tabla como "Step number", "Step description", "Comments".
- Encabezados de columna como "Input", "Output", "System".
- Textos como "Pruebas Funcionales".
- Listas de tipos de prueba.
- Entradas de tabla de contenido.
- Pasos internos numerados como "1.:", "2.:", "3.:".
- Reglas de negocio.
- Excepciones.
- Explicaciones internas del bloque.
- Validaciones subordinadas al requerimiento.

Ejemplo de contenido que NO debe devolverse:

"4.1 Configurar proceso"
"Pruebas Funcionales"
"Input"
"Output"
"System"
"Step number"
"Step description and screenshot"
"Comments"

Ejemplo de contenido que SÍ debe devolverse:

"Start process"
"Validate input data"
"Generate output"

Si un encabezado de sección y un ID estructurado aparecen juntos, el ID estructurado tiene prioridad para identificar el requerimiento, pero la salida final debe incluir solo el nombre funcional.

Ejemplo:

4.1 Configurar proceso
ABC.001.001 Start process

Devuelve únicamente:

"Start process"

NO devuelvas:

"4.1 Configurar proceso"
"ABC.001.001 Start process"

--------------------------------------------------
C. PDD Nestlé - "Process steps"
--------------------------------------------------

Los requerimientos pueden encontrarse dentro de una sección llamada:

"Process steps"

La sección puede estar numerada, por ejemplo:

"6.2. Process steps"
"6.3. Process steps"

La numeración puede variar. Lo importante es identificar la sección "Process steps".

En este formato los requerimientos pueden comenzar con "#" seguido de un número.

Ejemplo sintético:

#1 Open source system
#2 Enter input data
#3 Generate output

Devuelve:

"Open source system"
"Enter input data"
"Generate output"

No conviertas los pasos internos o explicaciones de cada bloque en requerimientos adicionales.

==================================================
PRIORIDAD DE BÚSQUEDA
==================================================

Busca en este orden:

1. Identificadores estructurados de requerimiento con patrón [PREFIJO].[NNN].[NNN].
2. "Acciones detalladas del proceso TO-BE" o sección equivalente de TO-BE.
3. "Process steps" o sección equivalente.
4. Una sección semánticamente equivalente que describa proceso futuro, requerimientos funcionales o pasos principales de la solución.

REGLA DE PRIORIDAD ABSOLUTA:

Si se detectan identificadores estructurados de requerimiento con patrón [PREFIJO].[NNN].[NNN], utiliza esa estructura como fuente principal y NO extraigas encabezados numéricos de sección como 4.1, 4.2, 4.3, etc.

Los nombres de sección anteriores son referencias frecuentes, pero no son un catálogo cerrado.

==================================================
REGLAS PARA REQUERIMIENTOS
==================================================

1. Identifica primero la estructura utilizada por el documento.
2. Si existen identificadores estructurados [PREFIJO].[NNN].[NNN], estos tienen prioridad sobre cualquier encabezado de sección.
3. Una vez identificada la estructura funcional principal, aplica el mismo criterio de extracción a todos los requerimientos de esa sección.
4. Conserva el orden en que aparecen.
5. Conserva el idioma original del título.
6. Devuelve únicamente el nombre funcional limpio del requerimiento.
7. No devuelvas IDs estructurados.
8. No devuelvas numeración de sección.
9. Extrae únicamente encabezados funcionales principales.
10. Excluye subrequerimientos.
11. Excluye subsecciones.
12. Excluye pasos internos.
13. Excluye explicaciones.
14. Excluye validaciones subordinadas a un requerimiento principal.
15. Excluye títulos generales del documento.
16. Excluye entradas de tabla de contenido.
17. Excluye encabezados de tabla.
18. Excluye nombres de columnas.
19. Excluye AS-IS.
20. Excluye objetivos, roles, hardware, software, volumetría, cronogramas y entregables.
21. Excluye secciones de "Tipos de prueba" o listas de pruebas aplicables.
22. No dupliques requerimientos.
23. No inventes requerimientos.
24. Si existe una jerarquía, selecciona el nivel padre y excluye sus descendientes.
25. Si no se identifica ninguna sección o estructura funcional válida, devuelve "requerimientos": [] y agrega una advertencia.

==================================================
REGLAS ESPECÍFICAS PARA FDD CON TABLAS
==================================================

Cuando el documento tenga tablas dentro de "Process Steps with screenshots" o una sección similar:

1. No uses los encabezados de color como requerimientos.
2. No uses el número de sección como requerimiento.
3. No uses encabezados de columna como requerimiento.
4. No uses "Tipo de prueba" como requerimiento.
5. No uses "Pruebas Funcionales" como requerimiento.
6. No uses "Input", "Output" o "System" como requerimiento.
7. Busca dentro de la tabla líneas con identificadores estructurados.
8. Usa el identificador estructurado para detectar el requerimiento real.
9. Devuelve únicamente el título funcional asociado al ID.
10. El contenido descriptivo debajo del ID pertenece al requerimiento, pero no debe devolverse como título.
11. Los pasos internos numerados dentro del bloque pertenecen al requerimiento padre y no deben convertirse en requerimientos separados.

Ejemplo sintético:

4.1 Configurar proceso
ABC.001.001 Start process
El sistema debe iniciar automáticamente...
1.: Cargar configuración.
2.: Registrar inicio.
Input Output System
NA NA NA

Devuelve únicamente:

"Start process"

NO devuelvas:

"4.1 Configurar proceso"
"ABC.001.001 Start process"
"El sistema debe iniciar automáticamente"
"1.: Cargar configuración"
"2.: Registrar inicio"
"Input"
"Output"
"System"

==================================================
CRITERIO DE VALIDACIÓN FINAL
==================================================

Antes de devolver la lista final de requerimientos, valida cada elemento:

Un elemento es válido si cumple al menos una de estas condiciones:

1. Es un encabezado principal dentro de "Acciones detalladas del proceso TO-BE".
2. Es un encabezado principal dentro de "Process steps".
3. Está asociado a un identificador estructurado con patrón [PREFIJO].[NNN].[NNN] y representa un título funcional.
4. Es un requerimiento funcional principal claramente distinguible dentro de una sección equivalente.

Un elemento NO es válido si cumple cualquiera de estas condiciones:

1. Es una entrada del índice.
2. Es un encabezado de tabla.
3. Es un nombre de columna.
4. Es una sección general.
5. Es un subpaso interno.
6. Es una regla de negocio.
7. Es una excepción.
8. Es una explicación.
9. Es una validación subordinada.
10. Es un tipo de prueba.
11. Es un título de sección sin ID estructurado cuando existen IDs estructurados en el documento.

Si después de aplicar estas reglas existen IDs estructurados, usa esos IDs solo para detectar los requerimientos, pero devuelve exclusivamente el nombre funcional limpio de cada requerimiento.

==================================================
2. EXTRACCIÓN DE TECNOLOGÍA
==================================================

Extrae la tecnología desde el PDD/FDD.

La tecnología corresponde a la herramienta, plataforma, framework, producto o entorno con el que se creó el flujo, RPA, bot, automatización o aplicación del proyecto.

Busca principalmente en secciones técnicas, arquitectura, alcance, descripción de solución, prerrequisitos, herramientas utilizadas, diagramas, tablas de tecnologías, plataformas, entorno de ejecución o menciones directas dentro del PDD/FDD.

Reglas obligatorias:

1. No uses el PAP como fuente de tecnología.
2. No confundas el tipo de solución con la tecnología utilizada.
3. Términos como "RPA", "automatización", "bot", "flujo automatizado", "proceso automatizado", "aplicación" o "sistema" describen la solución, pero NO son suficientes por sí solos para llenar tecnologia.valor.
4. La mayoría de las tecnologías con las que se trabaja son:
   - UiPath
   - Blue Prism
   - ServiceNow
   - Power Automate Cloud
   - Power Automate Desktop
   - Automation Anywhere
   - PowerApp
5. La lista anterior es una guía de tecnologías comunes, pero no es un catálogo cerrado. Si el PDD/FDD menciona claramente otra herramienta, plataforma o tecnología real usada para construir la solución, puedes devolverla.
6. Usa "explicita" cuando la tecnología aparezca directamente escrita en el PDD/FDD.
7. Usa "inferida" únicamente cuando la tecnología pueda deducirse con evidencia clara del propio PDD/FDD.
8. Si el documento solo menciona términos genéricos y no hay evidencia de una herramienta o plataforma específica, devuelve tecnología no encontrada.
9. No devuelvas valores genéricos como "RPA", "Bot", "Automatización", "Aplicación", "Sistema", "IA", "Software" o similares en tecnologia.valor.
10. Si aparecen varias tecnologías y el documento indica claramente que se usaron en el proyecto, devuelve los nombres separados por " / ".
11. Si aparecen varias tecnologías pero no queda claro cuál se usó para construir la solución, devuelve no encontrada.
12. Si no existe evidencia suficiente, devuelve exactamente:
   - "valor": null
   - "tipo_deteccion": "no_encontrada"
   - "justificacion": null

Ejemplos:

- Si el PDD/FDD dice "Power App", "Power Apps" o "PowerApp", devuelve "PowerApp" con tipo_deteccion "explicita".
- Si el PDD/FDD dice "Power Automate Desktop", devuelve "Power Automate Desktop" con tipo_deteccion "explicita".
- Si el PDD/FDD dice "ServiceNow" como sistema/plataforma usada por la solución, devuelve "ServiceNow" con tipo_deteccion "explicita".

==================================================
3. EXTRACCIÓN DEL CONTEXTO DEL PROCESO
==================================================

Extrae la siguiente información:

1. Descripción breve del proceso.
2. Calendario o frecuencia del proceso.
3. Cantidad de elementos procesados por periodo normal.
4. Cantidad de elementos procesados durante el periodo de máxima actividad.

Busca esta información principalmente en la descripción del proceso AS-IS, resumen del proceso, contexto del proceso, información general, volumetría o tablas equivalentes.

Etiquetas frecuentes:

- "Descripción breve del proceso"
- "Calendario y frecuencia del proceso"
- "# de elementos procesados / período de referencia"
- "Volumen de transacciones durante el periodo de máxima actividad(es)"

Los nombres pueden variar. Identifica los datos por su significado.

REGLAS DE EXTRACCIÓN

1. "descripcion_breve_proceso" debe resumir fielmente qué realiza el proceso.
2. No copies páginas completas.
3. "calendario_frecuencia" debe contener únicamente la frecuencia documentada.
4. No deduzcas la frecuencia.
5. "cantidad_periodo_normal" corresponde a los elementos procesados en el periodo normal o periodo de referencia.
6. "cantidad_periodo_maximo" corresponde al volumen de máxima actividad o periodo pico.
7. La cantidad del periodo máximo es opcional.
8. Extrae únicamente cantidades numéricas verificables.
9. No estimes ni extrapoles cantidades.

Las siguientes expresiones representan un dato NO proporcionado:

- "No especificado por el cliente"
- "N/A"
- "NA"
- "Por definir"
- "Pendiente"
- "No disponible"
- campo vacío

Cuando aparezcan, devuelve null.

Si una cantidad incluye el tipo de elemento, separa ambos valores.

Ejemplo:

500 facturas por día

Debe devolver:

{
  "cantidad": 500,
  "unidad_elemento": "facturas"
}

Si existen varias cantidades y no puedes identificar cuál corresponde al periodo normal o máximo, devuelve null para el campo ambiguo y agrega una advertencia.

==================================================
4. VALIDACIÓN DEL CÁLCULO DE INSUMOS
==================================================

Antes de realizar cálculos valida estos tres campos obligatorios:

1. descripcion_breve_proceso
2. calendario_frecuencia
3. cantidad_periodo_normal.cantidad

La cantidad del periodo máximo es opcional.

Si falta al menos un campo obligatorio:

- no realices ningún cálculo;
- no estimes valores;
- establece "estado_calculo": "error_validacion";
- agrega los nombres exactos de los campos ausentes en "datos_faltantes";
- establece "plan_insumos": null.

Utiliza este mensaje:

"[ERROR DE VALIDACIÓN: INSUMOS INSUFICIENTES] No es posible calcular la proyección de insumos porque faltan datos mandatorios en los requisitos. Acción requerida: proporcionar los datos ausentes para poder proceder con el cálculo del plan de capacidad y pruebas de estrés."

Aunque falle el cálculo de insumos, devuelve normalmente los requerimientos encontrados.

==================================================
5. REGLAS DE CÁLCULO DE INSUMOS
==================================================

Realiza los cálculos únicamente cuando estén disponibles los tres campos obligatorios.

BASE DE ESTRÉS

Si existe cantidad del periodo máximo:

base de estrés = cantidad del periodo máximo

En este caso establece:

"base_calculo_estres": "periodo_maximo"

Si no existe cantidad del periodo máximo:

base de estrés = cantidad del periodo normal

En este caso establece:

"base_calculo_estres": "periodo_normal"

No inventes un periodo máximo.

PRUEBA DE ESTRÉS

Calcula el 120% de la base de estrés.

Fórmula:

base_estres × 1.20

DEVELOPMENT

Asume tres fases de testing:

Fase 1:
50% del periodo normal.

Fase 2:
50% del periodo normal.

Fase 3:
120% de la base de estrés.

DEPLOYMENT / UAT

Devuelve únicamente un resultado para Deployment/UAT.

Deployment/UAT:
120% de la base de estrés.

Este resultado debe considerar insumos productivos y entorno productivo.

Agrega una nota indicando que para Deployment/UAT se considera el 120% con insumos productivos y entorno productivo, y que la diferencia aplica cuando cambia el tipo de insumos o el entorno utilizado para la ejecución.

REDONDEO

Si un resultado contiene decimales, redondea hacia arriba al siguiente número entero.

Ejemplo:

33 × 1.20 = 39.6

Resultado final:

40

No uses factores ni porcentajes diferentes a los especificados.
